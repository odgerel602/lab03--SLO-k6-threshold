## Алхам 2: Гурван чанарын сценарио (6 хэсэгтэй формат)

### 1. Performance сценарио — `/cart/add`-ийн хариу хугацаа

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэрэглэгч сагсанд бараа нэмэхэд систем хэвийн ачаалалд хурдан хариулна. |
| **Системийн төлөв** | API ажиллаж байна, бүх endpoint эрүүл, сервер дулаарсан (warm). |
| **Орчны төлөв** | Хэвийн ачаалал: 20 зэрэгцээ хэрэглэгч (VU) тогтмол 1 минут, нийт ≈ 45 хүсэлт/с (endpoint тус бүрт ≈ 15 хүсэлт/с). Localhost, сүлжээний саатал үгүй. |
| **Гадаад өдөөлт** | VU бүр ойролцоогоор секунд тутам `POST /cart/add` илгээнэ. |
| **Шаардлагатай хариу** | Систем HTTP 200 + `{ ok: true }` буцааж, сагсыг шинэчилнэ. |
| **Хэмжүүр** | `/cart/add` хүсэлтийн **95%** (p95) нь **50 мс**-ээс бага хугацаанд хариулна. |

### 2. Reliability сценарио — `/pay`-ийн эвдрэлийн давтамж

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Хэвийн хэрэглэгч төлбөр хийхэд төлбөрийн endpoint найдвартай ажиллана. |
| **Системийн төлөв** | API ажиллаж байна; төлбөрийн gateway хааяа timeout өгдөг (≈5% — серверт суулгасан). |
| **Орчны төлөв** | 20 VU тогтмол 1 минут, `/pay`-д ≈ 15 хүсэлт/с (нийт ≈ 900 төлбөр). |
| **Гадаад өдөөлт** | Хэвийн хэрэглэгчийн төлбөрийн үйлдэл: VU бүр секунд тутам `POST /pay`. |
| **Шаардлагатай хариу** | HTTP 200 + `{ paid: true }`; амжилтгүй бол 500 + алдааны мессеж (чимээгүй унахгүй). |
| **Хэмжүүр** | POFOD / error rate: `/pay` хүсэлтийн **8%-иас бага** нь 5xx алдаа буцаана (өөрөөр хэлбэл төлбөрийн хүсэлт бүр ≥ 92% магадлалтай амжилттай). |

### 3. Availability сценарио — сервер гэнэт унаад дахин асах

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Сервер гэнэт зогсоод (crash) дахин асахад систем хурдан сэргэж, нийт хүсэлтийн дийлэнх нь амжилттай байна. |
| **Системийн төлөв** | API хэвийн ажиллаж байгаад 2 минутын цонхны дунд **процесс гэнэт зогсоно** (Ctrl+C / kill). |
| **Орчны төлөв** | 20 VU тогтмол 2 минут, 3 endpoint бүгд ачаалалтай (≈ 45 хүсэлт/с). |
| **Гадаад өдөөлт** | **Эвдрэл (crash):** `node server.js` процесс зогсож, 10 секундийн дараа дахин асаагдана. |
| **Шаардлагатай хариу** | Дахин асмагц (≤ 1 с) хүсэлтийг хүлээж авч эхэлнэ; өгөгдөл/төлөв алдагдахгүй (stateless API). |
| **Хэмжүүр** | **Availability ≥ 90%** (амжилттай хүсэлт / нийт хүсэлт, 2 мин цонхонд); **сэргэх хугацаа (MTTR) ≤ 12 с** — процесс зогссоноос эхний амжилттай хариу хүртэл. |

### 4. Нэмэлт сценарио — `/report` latency

| Хэсэг | Агуулга |
|---|---|
| **Тойм** | Тайлан гаргах удаан endpoint хэвийн ачаалалд зөвшөөрөгдөх хугацаанд хариулна. |
| **Системийн төлөв** | API ажиллаж байна, тайлан 20 000 мөр буцаана (дизайнаар 200–400 мс). |
| **Орчны төлөв** | 20 VU тогтмол 1 минут, `/report`-д ≈ 15 хүсэлт/с. |
| **Гадаад өдөөлт** | VU бүр секунд тутам `GET /report`. |
| **Шаардлагатай хариу** | HTTP 200 + `{ rows: 20000 }`. |
| **Хэмжүүр** | `/report` хүсэлтийн **95%** (p95) нь **450 мс**-ээс бага. |

### "Сайн сценариогийн 5 шинж"-ээр шалгасан нь

- **Итгэмжтэй:** тоонууд бодит хэмжилтээс гарсан ([results/calibration.txt](results/calibration.txt)) — зохиомол биш.
- **Үнэ цэнэтэй:** сагс (орлогын урсгал), төлбөр (мөнгө), availability (бүх хэрэглэгч) — бизнест хамгийн чухал гурван зам.
- **Тодорхой:** өдөөлт бүрт endpoint, VU тоо, хүсэлт/с, хугацаа заасан.
- **Нарийн:** хэмжүүр бүр магадлалаар (p95, rate) ба нэгжтэй (мс, %, с) — "хурдан", "найдвартай" гэх мэт тодорхой бус үг үгүй.
- **Ойлгомжтой:** 6 хэсгийг хүснэгтээр салгасан тул хөгжүүлэгч ч, бизнесийн хүн ч уншиж чадна.

## Алхам 3: Сценариогоос SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | k6 threshold |
|---|---|---|---|---|
| Performance | `/cart/add` latency | **p95 < 50 мс** | 20 VU тогтмол, 1 мин | `http_req_duration{name:cart}: p(95)<50` |
| Reliability | `/pay` error rate | **< 8%** | 20 VU, 1 мин | `http_req_failed{name:pay}: rate<0.08` |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | **≥ 90%** | 2 мин, 10 с зогсолт орсон | `checks: rate>0.90` |
| Нэмэлт (report) | `/report` latency | **p95 < 450 мс** | 20 VU тогтмол, 1 мин | `http_req_duration{name:report}: p(95)<450` |

### Босго сонгосон үндэслэл

- **Performance 50 мс:** localhost дээр бодит p95 = 3.26 мс тул жишээний 200 мс нь юу ч хэмжихгүй сул босго; 50 мс нь Windows-ийн scheduler/GC-ийн саатлыг даах зайтай боловч 15 дахин удаашрах регрессийг барина.
- **Reliability 8%:** серверт 5% алдаа суулгасан ба ≈ 900 төлбөрийн дээж дээр стандарт хазайлт ≈ 0.7% тул 8% нь санамсаргүй хэлбэлзлээр FAIL болохгүй, харин алдаа бодитоор өсвөл барина.
- **Availability 90%:** хэвийн үед ч `/pay`-ийн 5% алдаа checks-ийн ≈ 1.7%-ийг "иддэг" тул 2 мин цонхонд 10 с орчим зогсолтыг тэсвэрлэх бодит босго.
- **Report 450 мс:** сервер дизайнаараа дээд тал нь 400 мс унтдаг тул 400 + 50 мс (сүлжээ/JSON) зай.

### Error budget (цагаар)

Availability SLO = 90%, цонх = 2 мин = 120 с:

```
Error budget = (1 − 0.90) × 120 с = 12 с "эвдрэх эрх"
```

Тэгэхээр 10 с зогсолт нь цагаар тооцоход budget-д (12 с) **багтах ёстой**. Алхам 5-д үүнийг хүсэлтээр дахин тооцно.

## Алхам 4: SLO → k6 threshold ([slo-test.js](slo-test.js))

Endpoint бүрийг `name` tag-аар ялгаж, threshold-ыг tag тус бүрд тавьсан. Босго нь дээрх SLO хүснэгттэй **яг ижил**:

```js
thresholds: {
  'http_req_duration{name:cart}':   ['p(95)<50'],   // Performance SLO
  'http_req_failed{name:pay}':      ['rate<0.08'],  // Reliability SLO
  'checks':                         ['rate>0.90'],  // Availability SLO
  'http_req_duration{name:report}': ['p(95)<450'],  // 4-р сценарио
},
```

Үр дүн ([results/pass.txt](results/pass.txt)) — 20 VU, 1 мин, нийт 2769 хүсэлт, **бүх threshold ✓, exit code 0**:

| SLO | Босго | Бодит | Үр дүн |
|---|---|---|---|
| `/cart/add` p95 | < 50 мс | 3.45 мс | ✓ PASS |
| `/pay` error rate | < 8% | 4.65% (43 / 923) | ✓ PASS |
| checks (availability) | > 90% | 98.44% (2726 / 2769) | ✓ PASS |
| `/report` p95 | < 450 мс | 395.3 мс | ✓ PASS |

## Алхам 5: Мини chaos ([results/chaos.txt](results/chaos.txt))

`k6 run --duration 2m slo-test.js` (threshold-ууд өөрчлөгдөөгүй, зөвхөн хугацааг CLI-аар 2 мин болгосон). Тест ажиллаж байх үед серверийг гэнэт зогсоож (`taskkill /F` — Ctrl+C-тэй адил процессыг шууд унагана), 10 с хүлээгээд `node server.js`-ийг дахин асаасан. Цагийн тэмдэглэл: [results/chaos-timeline.txt](results/chaos-timeline.txt)

```
20:14:58.544  k6 START (vus=20, duration=2m)
20:15:44.598  server STOP
20:15:55.349  server RESTART (node server.js)
20:16:03.028  first successful response after restart
20:17:00.695  k6 END
```

### k6-ийн гаралт

| SLO | Босго | Бодит | Үр дүн |
|---|---|---|---|
| checks (availability) | > 90% | **80.59%** (4630 / 5745) | ✗ **FAIL** |
| `/pay` error rate | < 8% | **21.93%** (420 / 1915) | ✗ **FAIL** |
| `/cart/add` p95 | < 50 мс | 4.21 мс | ✓ PASS |
| `/report` p95 | < 450 мс | 395.46 мс | ✓ PASS |

`http_req_failed` нийт **19.40% (1115 / 5745)** болж өссөн (хэвийн үед 1.55%). Зогсолтын үед 1047 хүсэлт `connectex: ... actively refused it` алдаагаар унасан — `/cart/add` 343, `/report` 352, `/pay` 352. k6 `thresholds on metrics 'checks, http_req_failed{name:pay}' have been crossed` гэж бичээд **exit code 99** буцаасан.

### Бодит availability (ХҮСЭЛТЭЭР)

```
Availability = амжилттай / нийт = 4630 / 5745 = 80.59%
Error budget (хүсэлтээр) = 10% × 5745 = 574 хүсэлт
Зарцуулсан = 1115 хүсэлт  →  budget-ийн ≈ 194% (бараг 2 дахин хэтэрсэн)
```

### Сэргэх хугацаа

- Бодит зогсолт (STOP → эхний амжилттай хариу): **20:15:44.6 → 20:16:03.0 = 18.4 с** — зорилтот 12 с-ээс **урт**.
- Үүнээс 10.7 с нь санаатай хүлээлт, **7.7 с** нь `node server.js` дахин асаж порт нээх хүртэлх хугацаа (Windows дээр процесс эхлүүлэх + Express ачаалах). Өөрөөр хэлбэл "10 с зогсолт" гэж төлөвлөсөн ч бодит сэргэх хугацаанд эхлүүлэх хугацааг нэмж тооцох ёстой байсан.

### Яагаад цагаар 12 с budget, хүсэлтээр өөр гарав?

Хэвийн үед VU-ийн нэг давталт ≈ 1.3 с (`/report`-ын 200–400 мс хүлээлт + `sleep(1)`) тул нийт ≈ **45 хүсэлт/с** (pass.txt: 45.26/s). Сервер унасан үед хүсэлт бүр `connection refused`-ээр **агшин зуур** буцдаг тул давталт ≈ 1.0 с болж, 20 VU × 3 хүсэлт ≈ **60 хүсэлт/с** болно — бодитоор 18.4 с-д 1047 алдаа = **57 хүсэлт/с**. Тэгэхээр зогсолтын нэг секунд хэвийн секундээс ≈ 1.3 дахин олон хүсэлт "иддэг". Үүнээс гадна `/pay`-ийн 5% алдаа (68 хүсэлт) budget-ийг хэвийн үед ч идсээр байдаг. Тиймээс:

- Цагаар: 18.4 с / 120 с = 15.3% унасан → 84.7% availability.
- Хүсэлтээр: 19.4% унасан → **80.59%** availability.
- Хэрэв зогсолт яг 10 с байсан ч: 10 с × ≈ 57 хүсэлт/с ≈ 570 + 68 (`/pay` 500) ≈ 640 алдаа > 574 budget → хүсэлтээр **мөн FAIL** болох байсан, харин цагаар (10 с < 12 с) PASS гэж харагдах байсан. Цагаар тооцсон budget нь хүсэлтээр тооцсоноос **өөдрөг** байдаг.

### Дүгнэлт: error budget хэтэрсэн

Budget бараг 2 дахин хэтэрсэн. Шалтгаан хоёулаа: (1) **зогсолт хэт урт** — 10 с биш 18.4 с болсон, учир нь дахин асах хугацааг төлөвлөөгүй; (2) **SLO хэт өөдрөг** — 90%-ийн budget-ийн ≈ 12% нь хэвийн үед `/pay`-ийн алдаанд зарцуулагддаг, мөн унасан үеийн хүсэлтийн урсгал хэвийнээс их. Бодит production-д сэргэлтийг автоматжуулах (systemd/pm2 restart, хэд хэдэн instance + load balancer) эсвэл SLO-гоо хүсэлтийн урсгалын өсөлтийг тооцож тогтоох хэрэгтэй.

### Reliability threshold яагаад мөн FAIL болсон бэ?

`/pay` error rate 21.93% (420 / 1915) болсон: үүнээс **352** нь сервер унасан үеийн `connection refused`, зөвхөн **68** нь серверийн жинхэнэ 500 алдаа (68 / 1563 хариулсан хүсэлт ≈ 4.4% — хэвийн 5% түвшинд). Өөрөөр хэлбэл **нэг эвдрэл (crash) хоёр SLO-г зэрэг зөрчсөн** — `http_req_failed` нь "сервер хариу өгсөн боловч алдаатай" ба "сервер огт байхгүй" хоёрыг ялгадаггүй.

**Тусгаарлах арга (нэг өгүүлбэрээр):** reliability SLI-г зөвхөн сервер хариу өгсөн (`status !== 0`) `/pay` хүсэлтүүдийн 5xx хувиар тусдаа custom `Rate` метрикээр хэмжиж, холболт тасарсан (`status === 0`) хүсэлтийг зөвхөн availability SLI-д тооцвол нэг crash хоёр SLO-г давхар зөрчихгүй.

## Алхам 6: Threshold-ыг зориуд эвдэх ([slo-test-fail.js](slo-test-fail.js))

`slo-test.js`-ээс ялгаатай нь зөвхөн нэг мөр:

```diff
-    'http_req_duration{name:report}': ['p(95)<450'],
+    'http_req_duration{name:report}': ['p(95)<100'],  // ЗОРИУД FAIL
```

Үр дүн ([results/fail.txt](results/fail.txt)):

```
    http_req_duration{name:report}
    ✗ 'p(95)<100' p(95)=395.46ms
...
level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
exit=99
```

- FAIL-ийг харуулж буй мөр: THRESHOLDS хэсгийн `✗ 'p(95)<100' p(95)=395.46ms` ба төгсгөлийн `level=error msg="thresholds ... have been crossed"`. Бусад гурван threshold ✓ хэвээр (checks 98.08%, cart p95 3.44 мс, pay 5.73%).
- **Exit code = 99** (Git Bash: `${PIPESTATUS[0]}` / `echo $?`, PowerShell: `$LASTEXITCODE`). PASS үед 0. CI pipeline (GitHub Actions, Jenkins) 0-ээс ялгаатай exit code-ыг алдаа гэж үзээд build-ийг зогсооно.
- Сервер `/report`-д дор хаяж 200 мс унтдаг тул p(95)<100 нь ямар ч машин дээр найдвартай FAIL болно.
- **Харин `/cart/add`-ыг p(95)<50 болгоход яагаад PASS хэвээр вэ?** — localhost дээр сүлжээний саатал байхгүй, endpoint ямар ч ажил хийхгүй шууд JSON буцаадаг тул p95 ≈ 3.4 мс; 50 мс-ээс 15 дахин хурдан. Манай `slo-test.js` аль хэдийн p(95)<50 ашиглаж PASS болж байгаа нь үүнийг харуулна. FAIL болгохын тулд босго бодит p95-аас доош (жишээ нь < 2 мс) байх ёстой — гэхдээ тийм босго машины хэлбэлзлээс хамаарч заримдаа PASS, заримдаа FAIL болох "flaky" threshold болно.

## Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү нь **босго тоог сонгох** байсан: жишээний 200 мс нь localhost дээрх 3 мс хариутай харьцуулахад юу ч хэмжихгүй тул бодит хэмжилт (calibration) хийж байж л утга учиртай босго гаргаж чадсан. Хоёр дахь хэцүү зүйл нь сценариогийн "Хэмжүүр" хэсгийн үгийг k6-ийн метрик рүү яг таг буулгах — жишээ нь "availability"-г k6 цагаар биш хүсэлтээр (`checks` rate) хэмждэг. PASS ажиллуулалтад бүх 4 threshold тэнцэж (cart p95 3.45 мс, pay 4.65%, checks 98.44%, report p95 395.3 мс), exit code 0 гарсан. Chaos туршилт миний availability сценариогийн хэмжүүрийг **үгүйсгэсэн**: 2 мин цонхонд 90% SLO-г "10 с зогсолтыг даана" гэж цагаар тооцсон боловч бодит availability хүсэлтээр 80.59% гарч, budget бараг 2 дахин хэтэрсэн. Шалтгаан нь сервер дахин асахад 7.7 с нэмэгдэж бодит зогсолт 18.4 с болсон, мөн унасан үед хүсэлт агшин зуур буцаж хэвийнээс ≈ 1.3 дахин олон хүсэлт алдагдсан явдал. Нэг crash нь availability ба reliability хоёр SLO-г зэрэг зөрчсөн тул SLI-гээ холболтын алдаа ба серверийн 5xx алдаагаар тусгаарлах шаардлагатайг ойлгосон. Зориуд эвдсэн тест k6 exit code 99 буцаадгийг харуулсан бөгөөд энэ нь CI-д чанарын шалгуурыг автоматаар хэрэгжүүлэх механизм юм. Эндээс SLO нь цаасан дээрх тоо биш, бодит эвдрэлээр шалгагдаж засагдах ёстой таамаглал гэдгийг ойлгосон. Дараагийн удаа availability SLO-д сэргэх хугацааг (MTTR) тусдаа тоогоор оруулж, error budget-ийг эхнээс нь хүсэлтээр тооцно.
